# TICKET-DB-006 — Generate identifiers in the database and make invoice numbering reliable (fixes user creation)

## Context
Business identifiers (`USR-NNN`, `TM-NNNNN`, `DEV-NNN`, `LR-NNNNN`) and invoice numbers (`FA-YYYY-NNNN`) are computed by the application as `count(*) + 1`. Existing user ids are not contiguous (`USR-001, 003, 005, 006`), so the next computed id already exists.

## Problem
- **User creation is broken today:** `POST /api/users` computes `USR-005`, which already exists, and returns 500.
- **After any deletion**, every `count()+1` generator recomputes an existing id. For devices, deleting `DEV-002` out of three blocks every further creation until the count catches up.
- **Invoice numbers** are derived from a row count filtered by `LIKE 'FA-YYYY-%'`, not from the last number issued. Any out-of-sequence or removed invoice causes a collision or a gap. Two concurrent creations get the same number (one then fails on the `UNIQUE` constraint). The `LIKE` cannot use the index because of the non-C collation (`French_Tunisia.1252`).
- The year is computed with the server's local `date.today()`.
- Formats are inconsistent: `TM-00` + 3 digits, `LR-00` + 3 digits, and a legacy `INV-2024-` prefix with the year hard-coded.
- No `IntegrityError` is handled. Collisions surface as 500 and leak SQL parameters to the log (TICKET-DB-004).

## Current Behavior
- Catalog check: the id generated by the API is `USR-005`, and it is already taken.
- Runtime: `POST /api/users` as admin → **500**, `UniqueViolation … users_pkey`.
- Query plan: `numero LIKE 'FA-2026-%'` scans the whole unique index, with no index condition.

## Expected Behavior
- Identifiers come from database sequences and never collide.
- Invoice numbers are unique, increasing, and gap-free if the business requires it (#38), attributed atomically even under concurrency.

## Technical Analysis
- Generators: `main.py:235`, `:337`, `:377`, `:401`, `:437`; `app/routers/invoicing.py:35-38`.
- `seed_users.py:85-95` already documents this exact trap and works around it with `max()`. The API does not.
- The integer surrogate keys use sequences correctly. Their gaps after rollbacks are normal and must never be used as business numbers.

## Root Cause
Application-side identifier generation without sequences, and without conflict handling.

## Impact
Admins cannot create accounts. Invoice numbering, a legal reference, is fragile.

## Proposed Solution
1. Per business prefix, a sequence resumed at the current maximum:
   ```sql
   CREATE SEQUENCE users_code_seq;
   SELECT setval('users_code_seq', (SELECT max(substring(id from 5)::int) FROM users WHERE id ~ '^USR-\d+$'));
   ```
   Generate the id as `'USR-' || lpad(nextval('users_code_seq')::text, 3, '0')`. Do the same for `TM`, `DEV` and `LR`, or move those tables to integer identity keys plus a derived display code. **Never renumber existing ids.**
2. Invoice numbering with a per-year counter row:
   ```sql
   CREATE TABLE invoice_counters (year int PRIMARY KEY, last_value int NOT NULL DEFAULT 0);
   -- inside the issuing transaction:
   INSERT INTO invoice_counters (year) VALUES ($1) ON CONFLICT DO NOTHING;
   UPDATE invoice_counters SET last_value = last_value + 1 WHERE year = $1 RETURNING last_value;
   ```
   The row lock serialises concurrent issuers. Attribute the number when the invoice is **issued**, not when the draft is created, if numbering must be gap-free (decision for #38).
3. One explicit business time zone for the issue date and the numbering year.
4. Catch `IntegrityError` and return 409.

## Acceptance Criteria
- [ ] `POST /api/users` as admin returns **201**, with an id above the current maximum.
- [ ] Deleting a device and then creating one succeeds.
- [ ] 20 concurrent invoice issuances produce 20 distinct, consecutive numbers.
- [ ] No `count()`-based id or number generation remains (`grep -n "count()+1"` is empty).
- [ ] Existing ids and numbers are unchanged.
